What must an agent do while it waits?

An agent often has to wait. A feed grows. A job runs. An API is slow. The usual answer is that the agent watches. This page shows what watching costs, the idea from 1960 that removes the cost, and what the measurements say. It also shows the parts that do not work yet.

1Watching fills the context

Give an agent one task. A feed of orders grows for 200 seconds. The agent must keep the total of each region. At some moment a column gets a new name, and the totals break. The agent must repair them and report the final totals.

First, let the agent do this alone. It has no other tool, so it reads the feed again and again. Each read adds a result to its context. Then give the same agent Uniselector, and measure the same quantity.

The brown line never stops. It goes from 5,852 to 26,993 tokens, and it would go on for as long as the feed does. The blue line has three short climbs and two flat parts. In the flat parts the agent is not there.

So who watches the feed while the agent is away?

2Two loops, not one

In 1960 W. Ross Ashby described a machine that stays alive in a world that it does not know. He named it the ultrastable system. It has two loops.

The first loop is fast. A part of the machine reacts to the world all the time. The second loop is slow. It watches only the essential variables: the few quantities that must stay inside limits. While they stay inside, the second loop does nothing. When one leaves its limits, the second loop changes the first loop by one step. Then it is silent again. In Ashby's Homeostat a stepping switch made that change. Its name was the uniselector.

Here is the same structure for an agent.

  • An object is a handle to data and one operation. It runs again when its source changes.
  • An essential variable is a sentence that the main agent writes, such as “The feed has fewer than 600 rows.”
  • The decision model is the detector. At one look it gives one probability for each sentence. It does not plan, and it does not repair.
  • A wake is the step. The runner of the broken object writes a new version behind the same name.

The main agent does not watch. It builds the thing that watches, and then it leaves.

3One look is one question for each sentence

What does the second loop see?

Three looks have a dot below 0.5, and each one is a wake. Wake 1 is a surprise. The main agent wrote a sentence about columns that the object does not show. The detector found that the sentence was not true, and the agent wrote a better one. Wake 2 is the new column name. Wake 3 is the end of the feed.

4A longer wait is almost free

Now the question that matters. Make the feed 3.3 times as long, from 60 s to 200 s.

What grows?

Alone, the longer feed added 62 turns, and the cost grew by 241%. With Uniselector it added 3 turns, and the cost grew by 3%. On the short feed the two are close. The second loop does not pay for itself until the wait is long.

The same design ran eight tasks of different kinds. Each answer was right.

5An object carries its runners

Who repairs a broken object?

Until now, the main agent did. But many repairs are small. So each object carries a short list of runners, in order. The first one can be a free local model. A runner is silent while each sentence is true: it makes no request, and it adds nothing to a look. When the check of the object fails, the runner makes one replacement, and the next look judges it with the same check. The list is in order: a wake that one runner does not close goes to the next runner, and the main agent is the last one. The handle never changes.

Here is one run of the 60 s task, second by second. At 20 s a column of the feed gets a new name.

Look 7 found the error of the new column name. The wake went to the local model, not to the main agent. The local model made one request: 2,726 tokens in 4.2 s. Look 9 judged the replacement, and each sentence passed, 6.0 s after the break. The main agent got one wake: the end of the feed.

What did that do to the session of the main agent?

The cost is one signal. It is not the grade. A binding is good when it moves work off the expensive agent and the variables stay inside their limits. So the grade has three questions.

Can the main agent define the runners? It did. It gave the object the list ["local", "top"] and a check of four sentences, and the text of the tools was its only guide.

Does the main agent sleep while the runner works? With no runner, the main agent got the wake of the break and used 3 turns for the repair. With the runners, the local model made the repair with one request, and the main agent got one wake: the end of the feed. The tokens of the run grew from 12,461 to 24,623. That added 0.2% of the base to the cost of the run.

Does the check guard the object? The check that found the break judges each replacement, and a replacement stays only when each sentence is true. Section 3 has the measure of the detector: 63 of 64.

6A runner is any callable

A runner is any callable: a model, a human, or a script that the agent wrote one minute ago. A summary or an embedding of an output is the same binding on an object that exists already, and a runner makes it only when a wake is due. One check shows the cost. Two runs watched the same feed, one with two forms and one with none. While nothing failed, each run spent the same 4,597 tokens in 5 looks. Then a new status came. The run with the forms woke 3.0 s later than the other one, and its wake had a summary that named the region of the new status.

The split between the two loops is the result. The cost of the main agent stayed flat while the wait grew, and the detector cost less than 1% of the cost of the main agent in each of the eight task runs.
